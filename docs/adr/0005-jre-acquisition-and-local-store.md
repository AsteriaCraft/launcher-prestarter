# ADR 0005. JRE: правильна архітектура, перевірка, атомарне встановлення і власне сховище

- Статус: запропоновано (етап Design, 2026-10-02); власне сховище - відкрите питання власнику з цим рішенням за
  замовчуванням
- Пов'язані: [0004](0004-windows-arm64-uses-x64-jre.md), [0006](0006-launching-the-launcher.md)

## Контекст (код `origin/release` 8b9cd54)

- `download.rs:48-55` шле `arch=aarch64`; API відповідає 400 (L-таблиця), `download.rs:66-68` мовчки бере аварійний
  JRE 25+37 (вересень 2025) з розміром `117540219`, правильним лише для Windows x64. Для інших архітектур функції
  без `return` не компілюються.
- Жодної перевірки завантаженого: ні `sha1`, який повертає API, ні розміру.
- `extract.rs:82` - `entry.unpack` без захисту від `../`; розпакування поверх наявного `JRE-25` (на Windows файли
  працюючої JVM заблоковані); архів лишається в сховищі (143 МБ, E3).
- `config.rs:42-48`: `dirs_next::data_dir()` + `GravitLauncherStore` - на Windows це Roaming (`%APPDATA%`), і цю назву
  ділять усі престартери Gravit на комп'ютері; `dirs-next` не підтримується.
- JRE перевстановлюється кожні 30 днів безумовно.
- API Liberica (перевірено 2026-10-02) повертає кілька записів (CSPU `25.0.4.1+1` і PSU `25.0.4+9`), поля
  `downloadUrl` (github.com/bell-sw/Liberica), `filename`, `size`, `sha1`, `version`, `featureVersion`,
  `packageType`, `bundleType`, `FX`, `GA`.

## Рішення

**Каталог JRE (`jre::catalog`)** - одна таблиця для всіх цілей:

| Престартер | Запит до API | Пакет | Каталог JRE |
|---|---|---|---|
| windows/x86_64 | `os=windows&arch=x86` | zip | `liberica-25-windows-x64-<версія>` |
| windows/aarch64 | `os=windows&arch=x86` ([0004](0004-windows-arm64-uses-x64-jre.md)) | zip | `liberica-25-windows-x64-<версія>` |
| linux/x86_64 | `os=linux&arch=x86` | tar.gz | `liberica-25-linux-x64-<версія>` |
| linux/aarch64 | `os=linux&arch=arm` | tar.gz | `liberica-25-linux-arm64-<версія>` |
| macos/x86_64 (зріз universal) | `os=macos&arch=x86` | tar.gz | `liberica-25-macos-x64-<версія>` |
| macos/aarch64 (зріз universal) | `os=macos&arch=arm` | tar.gz | `liberica-25-macos-arm64-<версія>` |

Завжди `bitness=64&bundle-type=jre-full&version-feature=25&version-modifier=latest`. Невідома ціль - помилка
компіляції (`compile_error!`), а не мовчазний `return`.

**Вибір запису:** лише `GA && FX && bundleType == "jre-full"` з потрібними ОС і архітектурою; з них найвища версія
(`25.0.4.1+1` вище за `25.0.4+9`). Порожній список - помилка API.

**Перевірка:**
- розмір завантаженого дорівнює `size` з API, `sha1` рахується потоком під час завантаження і порівнюється з `sha1`
  з API (два різні хости: api.bell-sw.com дає хеш, github.com - файл);
- аварійне джерело (лише коли API недоступний або відповів не так) - таблиця `src-tauri/src/jre/fallback.json`
  з URL, розміром і **sha256** для кожної цілі. Таблицю оновлює щотижневий workflow `jre-watch.yml` окремим PR
  (завантажує, рахує sha256), тож збирання відтворюване з коміту, а аварійний JRE не старіє на рік;
- після розпакування: є `bin/javaw.exe` (Windows) або `bin/java`, файл `release` містить `JAVA_VERSION="25…"`,
  і `java -version` завершується з кодом 0 за 15 с. Остання перевірка ловить JRE не тієї архітектури і macOS нижче
  11.0 до того, як гравець побачить «лаунчер не стартує».

**Встановлення - атомарне:**
1. перевірка вільного місця: розмір архіву + 3× розмір архіву (архів і розпакований JRE), з числами в повідомленні;
2. завантаження в `<сховище>/tmp/<filename>.part`;
3. розпакування в `<сховище>/jre/.staging-<випадково>`: zip через `enclosed_name()` (без `..` і абсолютних шляхів),
   tar через `unpack_in` (захист tar від виходу за межі); симлінки, що ведуть за межі каталогу, - відмова; права
   Unix зберігаються (E3 підтвердив, що `java` лишається виконуваним);
4. перейменування staging-каталогу у `jre/<каталог JRE>`; запис `state.json` через тимчасовий файл і rename;
5. видалення архіву і staging-каталогу (і після помилки);
6. на macOS - зняття `com.apple.quarantine` з власних файлів ([0003](0003-macos-delivery-and-signing.md)).

**Версії поруч, без перезапису.** Кожна версія JRE - свій каталог; `state.json` називає поточний. Старі каталоги
прибираються після успішного запуску з новим: лишаються поточний і попередній (JVM, запущена з попереднього, може
ще довантажувати нативні бібліотеки JavaFX), на Windows помилка видалення (файли зайняті) ігнорується до наступного
разу.

**Перевірка оновлень JRE - не частіше разу на 7 днів і ніколи не блокує гру.** На швидкому шляху (JRE готовий)
престартер запускає лаунчер одразу, якщо остання перевірка була менше 7 днів тому. Інакше питає API з тайм-аутом 3 с:
є новіша версія - показує вікно і ставить її, потім запускає лаунчер; немає мережі або API не відповів - запускає з
наявним JRE і спробує через 7 днів.

**Власне сховище замість `GravitLauncherStore`:**

| ОС | Каталог |
|---|---|
| Windows | `%LOCALAPPDATA%\Asterium\Prestarter` (Local, а не Roaming: 300 МБ JRE не мають їздити з профілем) |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/asterium/prestarter` |
| macOS | `~/Library/Application Support/Asterium/Prestarter` |

```
<сховище>/
  state.json                         schema 1: поточний JRE (каталог, версія, sha1, джерело, дата), дата перевірки,
                                     копія jar (sha256, дата, URL) - без персональних даних
  jre/liberica-25-<os>-<arch>-<версія>/
  launcher/Asterium.jar              лише для форматів з копією jar (AppImage, macOS)
  logs/prestarter-<1..5>.log         останні 5 запусків, до 1 МіБ кожен, домашній каталог записано як ~
  tmp/                               недокачані архіви (.part), чиститься на старті під .install.lock
  .install.lock                      блокування на час встановлення (другий запуск чекає і показує це)
```

Бібліотека шляхів - `dirs` (підтримується) замість `dirs-next`. Старий `GravitLauncherStore` престартер не читає і
не видаляє (його може використовувати інший проєкт на Gravit); FAQ сайту пояснює, що його можна видалити вручну.

## Наслідки

- Гравці Windows, які вже мають JRE у `GravitLauncherStore`, один раз завантажать ~120 МБ, коли до них дійде
  престартер 0.3.0 разом з оновленням лаунчера. Альтернатива (читати старе сховище) ризикує взяти JRE іншого
  проєкту і зберігає Roaming.
- ARM64-пристрої отримують актуальну JRE замість аварійної вересня 2025.
- Підроблений або обрізаний архів JRE не встановлюється; JVM, що працює, ніколи не перезаписується.

## Перевірка

- Модульні тести: вибір запису з реального JSON API (зафіксованого в `tests/fixtures`), каталог для всіх шести
  цілей, розбір `release`, архіви зі зловмисними шляхами (`../`, абсолютний шлях, симлінк назовні) для zip і tar,
  невідповідність sha1 і розміру, нестача місця, GC каталогів.
- Інтеграційні тести без GUI (`src-tauri/tests/`): локальний HTTPS-сервер з тестовим CA віддає API і маленький
  «JRE» (тестовий бінарник `fake-java`, що записує аргументи і середовище), повний шлях до запуску на всіх раннерах.
- CI smoke: справжнє завантаження з Liberica на кожній платформі (так, як у гравця).
