# ADR 0004. Windows ARM64: нативний престартер, JRE x64 під емуляцією

- Статус: запропоновано (етап Design, 2026-10-02); вибір JRE - відкрите питання власнику з цим рішенням за
  замовчуванням
- Пов'язані: [0001](0001-artifact-matrix-and-jar-delivery.md), [0005](0005-jre-acquisition-and-local-store.md)

## Контекст

- ARM64 exe збирається на Linux через cargo-xwin (виміряно, X1: PE32+ GUI AArch64, 4 496 896 B). WebView2 на
  Windows 11 ARM встановлено.
- **Нативна Liberica jre-full для Windows aarch64 не має WebKit і медіа JavaFX** (L2): у списку модулів є
  `javafx.web` і `javafx.media`, але немає `jfxwebkit.dll`, `jfxmedia.dll`, `gstreamer-lite.dll`, `glib-lite.dll`,
  `fxplugins.dll`; є лише `glass.dll`. У Azul немає JavaFX для Windows aarch64 зовсім.
- Рантайм Asterium використовує WebView (`asterium-launcher/src/main/java/pro/gravit/launcher/gui/scenes/web/*`,
  `WebPrewarm.java`): вікі, карта й інші вбудовані сторінки на нативній JRE не працюватимуть.
- Варіант самооновлення лаунчер бере з ОС і архітектури JVM (`LauncherRequest.java:48-103`): JVM x64 під емуляцією
  повідомляє `amd64`, тобто `EXE_WINDOWS_X86_64`, і оновлення завантажує `Asterium.exe` (x64) замість файла, з якого
  лаунчер запущено.
- Сьогоднішній код шле в API Liberica `arch=aarch64`, отримує 400 і мовчки бере старий аварійний JRE (L-таблиця;
  правильне значення - `arch=arm`).

## Рішення

1. Випускаємо нативний `Prestarter-windows-aarch64.exe`; LaunchServer збирає з нього `Asterium_arm64.exe`
   (варіант `EXE_WINDOWS_ARM64`), сайт пропонує його пристроям Windows на ARM.
2. **На Windows ARM64 престартер ставить JRE x64** (`os=windows&arch=x86`), а не нативну: таблиця можливостей у коді
   (`jre::catalog`) позначає `windows-aarch64` як «без WebKit» і переадресовує на `windows-x64`. Емуляція x64 є в
   Windows 11 on ARM.
3. Наслідок, який ми приймаємо явно: перше самооновлення лаунчера перезапише файл гравця збіркою
   `Asterium.exe` (x64 престартер + jar). Поведінка після цього та сама (x64 престартер на ARM ставить той самий JRE
   x64 у той самий каталог, [0005](0005-jre-acquisition-and-local-store.md)), лише сам престартер працює під
   емуляцією кілька секунд.
4. `EXE_WINDOWS_ARM64` на сервері все одно отримує URL і хеш ([0010](0010-launchserver-variants-and-static-downloads.md)),
   щоб перехід на нативну JRE був зміною одного рядка в престартері.
5. **Умова переходу на нативну JRE:** у jre-full для Windows aarch64 з'являється `jfxwebkit.dll`. Щотижневий
   workflow `jre-watch.yml` читає центральний каталог zip через HTTP Range (як L2) і відкриває issue, коли файл
   з'являється. Альтернатива - рантайм навчиться показувати вбудовані сторінки в браузері, коли WebView немає (це
   зміна в asterium-launcher, не тут).

## Наслідки

- Повна функціональність лаунчера на Windows ARM (вбудовані сторінки, медіа) ціною емуляції UI лаунчера. Гра
  (клієнт Minecraft) запускається окремою JVM, яку обирає лаунчер за профілем, і це рішення її не стосується.
- Файл «для ARM» після першого оновлення стає x64-збіркою. Сайт не обіцяє «нативний ARM-лаунчер», а пише
  «збірка для Windows на ARM (Snapdragon)»; FAQ пояснює, що x64-збірка теж працює.

## Розглянуті варіанти

- Нативна JRE aarch64 з деградацією вбудованих сторінок. Швидший UI лаунчера, але зламані вікі й карта. Можна
  обрати замість рішення за замовчуванням (відкрите питання власнику).
- Не випускати ARM64 збірку, давати x64. Суперечить рішенню власника про цілі.
- Передавати JVM `-Dos.arch=aarch64`, щоб лаунчер називав себе ARM64. Відкинуто: лаунчер за цією властивістю обирає
  ще й Java і нативні бібліотеки для клієнтів, а JVM x64 не може їх завантажити.

## Перевірка

- Модульний тест таблиці: `windows/aarch64` → API `arch=x86`, пакет `zip`; `linux/aarch64` і `macos/aarch64` →
  `arch=arm`.
- `windows-11-arm` у CI: ARM64 exe з дописаним `Hello.jar` → справжній JRE x64 → маркер; `Hello.jar` друкує
  `os.arch=amd64`. Окремо x64 exe на тому самому раннері.
- `jre-watch.yml`: тест на зафіксованому списку файлів (є/немає `jfxwebkit.dll`).
