# ADR 0004. Windows ARM64: нативний престартер, JRE x64 під емуляцією

- Статус: запропоновано (етап Design, 2026-10-02); вибір JRE - відкрите питання власнику з цим рішенням за
  замовчуванням; переглянуто після рецензії дизайну 2026-10-02 (див. «Ревізія»)
- Пов'язані: [0001](0001-artifact-matrix-and-jar-delivery.md), [0005](0005-jre-acquisition-and-local-store.md)

## Контекст

- ARM64 exe збирається на Linux через cargo-xwin (виміряно, X1: PE32+ GUI AArch64, 4 496 896 B). WebView2 на
  Windows 11 ARM встановлено.
- **Нативна Liberica jre-full для Windows aarch64 не має WebKit і медіа JavaFX** (L2): у списку модулів є
  `javafx.web` і `javafx.media`, але немає `jfxwebkit.dll`, `jfxmedia.dll`, `gstreamer-lite.dll`, `glib-lite.dll`,
  `fxplugins.dll`; є лише `glass.dll`. У Azul немає JavaFX для Windows aarch64 зовсім.
- Рантайм Asterium використовує WebView (`asterium-launcher/src/main/java/pro/gravit/launcher/gui/scenes/web/*`,
  `WebPrewarm.java`): вікі, карта й інші вбудовані сторінки на нативній JRE не працюватимуть.
- Варіант самооновлення лаунчер бере з ОС і архітектури JVM (`LauncherRequest.java:48-103`): JVM x64 під емуляцією
  повідомляє `amd64`, тобто `EXE_WINDOWS_X86_64`, і оновлення завантажує `Asterium.exe` (x64) замість файла, з якого
  лаунчер запущено.
- Сьогоднішній код шле в API Liberica `arch=aarch64`, отримує 400 і мовчки бере старий аварійний JRE (L-таблиця;
  правильне значення - `arch=arm`).

## Рішення

1. Випускаємо нативний `Prestarter-windows-aarch64.exe` у кожному релізі: CI його збирає і проганяє smoke на
   `windows-11-arm`, AsteriumReleases його встановлює. Але **поки JRE на ARM - x64, гравцям його не роздаємо**:
   варіант `EXE_WINDOWS_ARM64` на LaunchServer вимкнено (немає `launcherVariant` у конфігу), а сайт пропонує
   пристроям Windows 11 на ARM звичайний `Asterium.exe` («працює на ARM через емуляцію x64»,
   [0011](0011-site-download-experience.md)).
   Причина (рецензія, перевірено в коді Gravit): лаунчер називає варіант за архітектурою JVM
   (`LauncherRequest.java:25-39`), JVM x64 - це `EXE_WINDOWS_X86_64`; `LocalUpdatesProvider.java:110-113` порівнює
   SHA-512 запущеного файла з хешем `Asterium.exe`, ARM-збірка ніколи не збігається, і `LauncherBackendImpl.init`
   замінює файл ще до входу. Тобто `Asterium_arm64.exe` прожив би рівно один запуск, гравець завантажив би 13 МБ
   двічі, а нативний ARM-престартер не дійшов би ні до кого.
2. **На Windows ARM64 престартер ставить JRE x64** (`os=windows&arch=x86`), а не нативну: таблиця в коді
   (`jre::catalog`) позначає `windows-aarch64` як «без WebKit» і переадресовує на `windows-x64`. Це стосується і
   x64-престартера, запущеного під емуляцією (`Asterium.exe` на ARM), і нативного.
3. **Без емуляції x64 (Windows 10 on ARM)** нативний престартер ставить нативну JRE aarch64 (лаунчер працює без
   вбудованих сторінок і медіа) і пише це в журнал: x64 JRE там не запуститься. Перевірка -
   `GetMachineTypeAttributes(IMAGE_FILE_MACHINE_AMD64)` (Windows 11), а якщо функції немає - емуляції немає.
   x64 `Asterium.exe` на Windows 10 on ARM не запускається зовсім, тому сайт показує цим пристроям «не
   підтримується» ([0011](0011-site-download-experience.md)).
4. **Перехід на нативну JRE** - одна зміна в каталозі престартера плюс увімкнення `EXE_WINDOWS_ARM64` на
   LaunchServer і кнопки ARM на сайті, разом. Тоді JVM повідомляє `aarch64`, лаунчер питає `EXE_WINDOWS_ARM64` і
   оновлює файл тією самою збіркою.
5. **Умова переходу:** у jre-full для Windows aarch64 з'являється `jfxwebkit.dll`. Щотижневий workflow
   `jre-watch.yml` читає центральний каталог zip через HTTP Range (як L2) і відкриває issue, коли файл
   з'являється. Альтернатива - рантайм навчиться показувати вбудовані сторінки в браузері, коли WebView немає (це
   зміна в asterium-launcher, не тут).

## Наслідки

- Повна функціональність лаунчера на Windows 11 on ARM (вбудовані сторінки, медіа) ціною емуляції UI лаунчера і
  самого престартера. Гра (клієнт Minecraft) запускається окремою JVM, яку обирає лаунчер за профілем, і це рішення
  її не стосується.
- Гравець на ARM має той самий `Asterium.exe`, що й на x64: один файл, одне самооновлення, жодної заміни файла.
- Нативна ARM-збірка перевірена в кожному релізі і готова до вмикання, але не роздається.

## Розглянуті варіанти

- Нативна JRE aarch64 з деградацією вбудованих сторінок. Швидший UI лаунчера, але зламані вікі й карта. Можна
  обрати замість рішення за замовчуванням (відкрите питання власнику).
- Не випускати ARM64 збірку, давати x64. Суперечить рішенню власника про цілі.
- Передавати JVM `-Dos.arch=aarch64`, щоб лаунчер називав себе ARM64. Відкинуто: лаунчер за цією властивістю обирає
  ще й Java і нативні бібліотеки для клієнтів, а JVM x64 не може їх завантажити.

## Перевірка

- Модульний тест таблиці: `windows/aarch64` з емуляцією → API `arch=x86`, пакет `zip`; без емуляції → `arch=arm`;
  `linux/aarch64` і `macos/aarch64` → `arch=arm`.
- `windows-11-arm` у CI: і ARM64 exe, і x64 exe з дописаною FX-пробою → справжній JRE x64 → маркер; проба друкує
  `os.arch=amd64` і відкриває WebView (`jfxwebkit.dll` під емуляцією).
- `jre-watch.yml`: тест на зафіксованому списку файлів (є/немає `jfxwebkit.dll`).
- e2e LaunchServer (лейн server): `LauncherSignCheck` як `EXE_WINDOWS_X86_64` з дайджестом ARM64-файла → точна
  URL `Asterium.exe` (фіксує поведінку з пункту 1).

## Ревізія після рецензії (2026-10-02)

| Знахідка рецензії | Що змінено |
|---|---|
| `Asterium_arm64.exe` замінюється x64-збіркою на першому запуску, а не «на наступному оновленні» | варіант A рецензії: ARM-пристроям - `Asterium.exe`, `EXE_WINDOWS_ARM64` вимкнено до нативної JRE, ARM-збірка лише будується і тестується |
| Windows 10 on ARM не має емуляції x64 | перевірка емуляції в нативному престартері, нативна JRE як запасний шлях; сайт: «не підтримується» для Windows 10 on ARM |
